# Teaching Slide Package

台本や文字起こしを、講師がそのまま使える教材スライドへ変換する。内容設計を先に完了し、画像生成は必ず最後のビジュアル制作工程に置く。

## URLから完成画像までの標準直通フロー

YouTube URLが入力された場合は、別Skillの存在を探し直さず、このSkill内で次を一続きに実行する。

1. `yt-dlp` で動画メタデータと日本語字幕を取得する。
2. 字幕を時系列の素材として読み、対象者、課題、到達点、中核主張、具体例、最終行動を抽出する。
3. 文字起こし順をそのまま使わず、学習者の理解順へ再構成する。
4. 全スライドのタイトル、表示文言、講師台本、時間、構図を確定し、内容を凍結する。
5. `imagegen` Skillを読み、Codex組み込み `image_gen` で1枚ずつ完成画像を生成する。
6. 全画像を実寸とモンタージュで検証する。
7. ソース、設計、生成プロンプト、画像、検証結果を同じパッケージへ保存してZIP化する。

ユーザーが途中確認を求めていない限り、構成案だけで停止せず、検証済み画像とZIPまで完了する。外部調査を追加するのは、字幕だけでは重大な事実を確認できない場合またはユーザーが明示した場合に限る。URL取得のために `yt-dlp` を使うことを、別Skillの発動と誤認しない。

## 絶対ルール

1. **内容先行**: 台本理解、教材構成、表示内容、講師台本、時間計算を終えるまで画像を生成しない。
2. **1スライド1テーマ**: 1枚に複数の主張を詰め込まない。タイトルはその1枚の結論にする。
3. **素の教材デザインを標準にする**: 白背景、太い黒見出し、青い罫線、黒と青の線画図解を共通の見た目にする。内容に応じて比較、工程、関係図などの構成だけを変える。
4. **構成は内容別**: 共通トークンを、全枚同一レイアウトと取り違えない。比較、工程、階段、円環、関係図など、テーマに最適な構成を選ぶ。
5. **時間は講師台本から計算**: 1分300文字で、各スライドと全体の時間を算出する。
6. **スマホで読める密度**: 16:9の全体表示でもタイトル、数字、主要語が判読できる大きさにする。
7. **画像を見せる依頼には画像で答える**: ローカルパス、PPTX、灰色のプレースホルダーを「チャットに表示した画像」の代わりにしない。
8. **PPTXは明示依頼時のみ**: 目視確認はPNGで行う。PPTXが必要なら、検証済みPNGまたは確定済み設計から最後に組み立てる。
9. **動画を識別できる出力**: 複数動画を連続処理しても混同しないよう、出力フォルダ、ZIP、レポート、画像一覧に開催日または収録日と動画固有slugを含める。
10. **標準配色を固定**: 背景は白、本文は黒、強調は鮮明な青、補助は薄いグレーとする。ロゴや装飾的なブランド表現は、ユーザーが明示した場合だけ追加する。
11. **表紙とCTAを必須化**: 全デッキの先頭に動画固有の表紙、末尾に受講後の具体的行動を示すCTAスライドを必ず入れる。

## ワークフロー

### Step 1｜入力を特定する

1. 入力がYouTube URLか、ローカル台本・文字起こしかを判定する。
2. YouTube URLの場合は出力先に `source/` を作り、次の情報を取得する。
   - `yt-dlp --dump-single-json --skip-download <URL>` 相当の動画タイトル、チャンネル、公開日、収録時間、チャプター、元URL
   - `yt-dlp --write-auto-subs --write-subs --sub-langs "ja-orig,ja" --sub-format json3 --skip-download <URL>` 相当の日本語字幕
3. 字幕は手動字幕を優先し、なければ自動字幕を使う。日本語字幕が取得できない場合だけ、利用可能言語、説明欄、音声文字起こしの順で代替経路を検討し、取得できなかった事実を明示する。
4. 複数URLが同じ依頼内にあり、ユーザーが統合を求めた場合は、各URLの出典を保持したまま1つの教材へ統合する。統合指定がなければ動画ごとに分ける。
5. ローカル入力の場合は、指定フォルダと配下フォルダから台本候補の `.md` を列挙する。
6. 同名の `.wav` と `.md` がある場合、内容設計には `.md` を優先する。音声を再文字起こししない。
7. 複数台本がある場合は、ファイル名、題名、文字数を整理して対象を確定する。
8. 対象台本または字幕は要約部分だけでなく、必要な範囲の全文を読む。
9. 参考スライド画像がある場合は先に目視し、デザイントークンだけを抽出する。この時点では新規画像を生成しない。

台本から抽出するもの:

- 対象受講者
- 受講前の悩み
- 受講後にできること
- 中核となる主張
- 主張を支える理由、具体例、ワーク
- 最後に実行させる行動

### Step 2｜教材の背骨を決める

文字起こしの時系列をそのままスライド化しない。重複、脱線、挨拶、質疑応答を整理し、学習者の理解順に再構成する。

推奨する基本の流れ:

1. 自分ごと化: なぜ今この話が必要か
2. 全体像: 何を理解すればよいか
3. 理解: 原理、判断基準、手順
4. 体験: 具体例、比較、ワーク
5. 行動: 明日から何をするか

全体のゴールは「理解した」ではなく、観察可能な行動で書く。

### Step 3｜スライドマップを作る

画像生成より前に、全スライドについて以下を確定する。

| 項目 | 内容 |
|---|---|
| `number` | 連番 |
| `title` | その1枚の結論。原則1行 |
| `theme` | 1つだけ |
| `role` | 導入、理解、証拠、ワーク、まとめ等 |
| `visible` | 画面に出す文字、数字、図の関係 |
| `layout` | 内容に適した構成案 |
| `layout_family` | Focus、Compare、Sequence、Evidence、Quote、Demo等 |
| `script` | 講師が話す文章 |

タイトルだけを順番に読んでも、講義の論理が通るようにする。隣接スライドと同じ結論を言い換えただけの重複を残さない。

スライドマップには次の2枚を必ず含める。

- `cover`: 動画・講座固有の題名と、必要なら短い副題を表示する先頭スライド
- `cta`: 受講者が講義後に実行する具体的な1アクションを中心にした最終スライド。「ありがとうございました」だけで終えない

### Step 4｜表示内容と講師台本を書く

表示内容:

- タイトルは原則1行
- 本文は要点だけに絞り、台本全文を載せない
- 強調する数字、対比、順序を視覚化する
- 長文段落を置かない
- 図に不要な装飾や説明文を足さない

講師台本:

- スライドに書いていない理由、例、つなぎを話す
- 表示内容を読み上げるだけにしない
- 1枚の中で次のテーマへ脱線しない
- 教材として再利用できる自然な話し言葉にする

### Step 5｜時間を計算する

講師台本の本文文字数を数える。メタデータ、見出し記号、時間表示は除外し、日本語の句読点は文字数に含める。

```text
duration_minutes = script_characters / 300
duration_seconds = round(script_characters / 300 * 60)
```

各スライドに以下を記録する。

```text
文字数: 205字
目安時間: 0:41
```

全体時間は各スライドの文字数合計から同じ式で計算する。平均時間だけで済ませず、各スライドの実数を出す。ワーク、質疑、操作待ちの時間は台本時間と分け、含める場合は別項目で明示する。

### Step 6｜内容を凍結して検証する

画像生成へ進む前に、次をすべて満たすこと。

- [ ] 1枚につき主張は1つ
- [ ] 全タイトルが重複していない
- [ ] タイトル列だけで講義の流れが通る
- [ ] 対象受講者と到達点が明確
- [ ] 表示内容と講師台本が矛盾しない
- [ ] 各台本の文字数と時間が計算済み
- [ ] 最終スライドが具体的な行動で終わる
- [ ] 画像に入れる文言が確定済み

1項目でも未完了なら画像を生成しない。

### Step 7｜デザイントークンを確定する

参考画像がある場合は、その画像から以下を抽出して全枚で固定する。

- アスペクト比と画像サイズ
- 背景色、主色、本文色、補助色、罫線色
- 日本語書体の系統と太さ
- タイトル位置、タイトル下線、外側余白
- アイコンの線幅、塗り、角の扱い
- 強調ラベル、番号、矢印の形

参考画像がない場合の教材用デフォルト:

```text
ratio: 16:9
canvas: 1672 x 941
background: #FFFFFF on every slide, including cover and CTA
primary: #075AC8
text: #0A0A0A
secondary-background: #F2F2F2
border: #929292
type: bold modern Japanese gothic sans-serif
title: very large bold black headline at top; keep to one line when possible
title-rule: thin vivid-blue horizontal rule directly below the headline
graphics: simple black-and-blue line icons, arrows, number circles, checkmarks
layout: select comparison, flow, timeline, staircase, Venn, funnel, calculation, or focus according to content
logo: none by default; add only when explicitly requested
radius: modest; do not card every item
```

**全動画で統一するのは、白・黒・青の視覚言語と読みやすさである。各スライドの情報配置は内容に合わせて変える。**

### シリーズの統一基準

動画が変わっても、次を標準として統一する。

- 純白 `#FFFFFF` の背景
- 太く大きな黒い結論型タイトル
- タイトル直下の細い青線
- 強調色 `#075AC8`
- 本文色 `#0A0A0A`
- 補助面 `#F2F2F2`、罫線 `#929292`
- 太い日本語ゴシック
- 黒と青の単純な線画アイコン
- 青い番号円、矢印、チェック、見出し帯
- 1スライド1テーマ
- スマホ全体表示で読める文字量
- 表紙と具体的なCTA

動画やスライド内容に応じて変えるのは、情報構造だけとする。

- 比較なら左右比較
- 手順なら横フローまたは階段
- 因果なら矢印
- 関係ならベン図または接続図
- 数値なら大きな数字と計算式
- 対象者なら人物と属性の対応
- 絞り込みならファネル
- 行動なら1つのCTA

配色テーマ、アートディレクション、写真処理、装飾モチーフを毎回設計しない。動画の識別は表紙タイトルと出力名で行う。

内容に応じた構成例:

- 二者比較: 左右比較、Before/After
- 手順: 横フロー、縦階段、タイムライン
- 因果: 原因から結果への矢印
- 循環: 円環、改善ループ
- 共通領域: ベン図
- 優先順位: ピラミッド、絞り込み
- 関係者: ステークホルダーマップ
- 数値効果: 大きな数値と計算式
- 単一概念: 中央の大図解と短い定義

## Codex ImageGenへのHandoff（スライド画像生成）

画像生成は外部APIアダプターを設計せず、Codexの組み込み `image_gen` を直接使う。画像生成前に `imagegen` スキルを読み、その組み込みツール経路に従う。CLI/APIフォールバックへ切り替えない。

1. 参考画像がローカルにある場合は、まず `view_image` で目視する。
2. 参考画像は編集対象ではなく、配色、タイポグラフィ、線、余白、情報密度の参照として扱う。
3. 各スライドは別々の `image_gen` 呼び出しで生成する。異なるテーマを1回の複数候補生成で代用しない。
4. 各呼び出しへ、共通デザイントークンと当該スライドだけの確定仕様を渡す。
5. 実際に渡した全プロンプトを `image-prompts.json` へスライド番号と対応づけて保存する。
6. 組み込み出力を最終パッケージの `images/cover.png`、`images/slide-NN.png`、`images/cta.png` へコピーし、生成画像を既定保存先だけに残さない。
7. ユーザーがチャット表示を求めた画像は、`generatedImage(result)` で実画像として返す。ローカルパスだけを表示結果にしない。
8. 日本語の誤字、余計な文字、構成崩れがあれば、その画像だけを対象に1変更ずつ再生成する。

このHandoffは画像生成手段だけをCodexへ置き換える。内容先行、画像は最終ビジュアル工程、共通トークン、内容別構成、全画像検証という絶対ルールは変更しない。

### Step 8｜画像を最終ビジュアル工程で生成する

Step 1〜7が完了してから、Codex組み込み `image_gen` を使って1枚ずつPNGを作る。

画像生成プロンプトには必ず含める:

- 共通デザイントークン
- 当該スライドの確定タイトル
- 画面に表示する確定文言
- 図の要素数と位置関係
- 内容に適したレイアウト
- 16:9と統一画像サイズ
- 日本語文字を正確に描く指示
- 余計な文章、ロゴ、透かしを追加しない指示

組み込み `image_gen` 用のプロンプトは、次の順で組み立てる。

```text
Use case: productivity-visual / scientific-educational
Asset type: Japanese teaching slide
Primary request: 確定済みの1スライドを完成画像として描画
Reference image: デザイントークンのみ参照
Text (verbatim): タイトルと表示文言を引用符付きで列挙
Composition: layoutで確定した要素数、位置、関係
Color palette: 共通トークンのHEX値
Typography: 太い日本語ゴシック、スマホ全体表示でも読める大きさ
Constraints: 16:9、1スライド1テーマ、余白確保、文字切れなし
Avoid: 余計な文字、ロゴ、透かし、写真調背景、装飾優先、同一構成の反復
```

参考画像を使う場合は、ローカルファイルを `referenced_image_paths` に渡す。新規生成なので `num_last_images_to_include` と同時に使わない。

禁止:

- 台本理解前の画像先行
- 画像を見てから主張を後付け
- 全スライドへ同じ2カラム構成を強制
- 装飾写真を主役にして教材内容を弱める
- 画像生成AIが勝手に作った文言を採用
- 文字が確定していない状態での一括生成
- 前回デッキを複製し、文字、写真、色だけを差し替える
- 内容を読む前にテーマ、配色、表紙構図を決める
- 別動画で同じ表紙構図、CTA構図、署名的モチーフを再使用する
- 違って見せることだけを目的に書体や装飾を変更する
- 1動画内に無関係なアートディレクションを混在させる
- 雰囲気だけのストック写真、AIロボット、AI脳、回路、青い発光、グラデーション球を使う
- 24pt相当未満へ文字を縮めて情報を詰め込む
- 色だけで正誤、分類、警告、順序を表す
- コントラスト未検証の文字を写真へ直接重ねる

### Step 9｜全画像を検証する

1. 全画像を同じ解像度へ統一する。
2. 各画像を実寸で開き、タイトル、本文、数字、日本語の崩れを確認する。
3. 全枚のモンタージュを作り、講義全体の統一感とレイアウトの単調さを確認する。
4. 白紙、破損、極端に小さい文字、切れ、重なりがないことを確認する。
5. 参考画像から抽出した色、線、余白、書体のルールが全枚で維持されていることを確認する。
6. 通常文字4.5:1以上、大きな文字3:1以上のコントラストを確認する。
7. 色を消しても、ラベル、形、位置、線種から意味が通ることを確認する。
8. 25%縮小表示とスマートフォン全体表示で、タイトルと視覚的主役を即座に識別できることを確認する。
9. 同一レイアウトの3枚連続使用とLayout Family不足を検出する。
10. 全枚モンタージュで、白・黒・青の統一感と同一レイアウトの過剰反復がないことを確認する。
11. 画像数、各画像の幅・高さ、破損・白紙判定、統一解像度、総合PASS/FAILを `image-validation.json` に保存する。

検証に落ちた画像だけを再生成し、内容まで無断で変更しない。

### Step 10｜一式を納品する

標準パッケージ:

```text
{date}-{video-slug}-slide-package/
├── deck-spec.json
├── deck-content-and-script.txt
├── source-info.json
├── image-prompts.json
├── image-validation.json
├── images/
│   ├── cover.png
│   ├── slide-01.png
│   ├── ...
│   └── cta.png
├── source/
│   ├── video.info.json
│   └── video.ja-orig.json3
└── montage.png
{date}-{video-slug}-slide-package-complete.zip
```

`source-info.json` には最低限、動画タイトル、元URLまたは元ファイル、収録時間、処理日、`video-slug` を記録する。表紙タイトルとファイル名の両方から、どの動画の教材か判別できる状態にする。

`deck-content-and-script.txt` には各スライドの以下を人が読める形で入れる。

- 番号
- タイトル
- 表示内容
- 講師台本
- 台本文字数
- 300文字/分換算の時間

`deck-spec.json` は同じ情報を機械処理可能な構造で保持する。`image-prompts.json` は再生成可能なプロンプト、`image-validation.json` は画像検証結果を保持する。PPTXまたはGoogle Slides化はユーザーが明示した場合のみ追加する。

## チャット表示のルール

ユーザーが「このチャット画面に画像を出せ」「スマホで見せろ」と指定した場合:

1. 画像生成ツールの実画像出力を、その応答内に表示する。
2. `C:\...\image.png` のようなローカルパスをMarkdown画像として返し、表示できた扱いにしない。
3. PPTXリンクやフォルダリンクだけを返さない。
4. まず1枚の試作を求められた場合は、内容を確定した1枚だけ生成して表示し、勝手に全枚生成へ進まない。

ユーザーが「内容だけ出せ」と指定した場合は、画像やPPTXを作らず、表示内容、講師台本、時間をチャット本文へ直接出す。

## 完了報告

完了時は最低限、以下を伝える。

- スライド枚数
- 台本合計文字数
- 300文字/分換算の合計時間
- 生成画像数と検証結果
- 内容・台本ファイル、画像フォルダ、モンタージュ、ZIPの保存先
- PPTXを作ったか、作っていないか

未検証の項目を「確認済み」と報告しない。
