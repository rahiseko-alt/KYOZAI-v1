# setup

上から順に実行する。前の手順が終わるまで次に進まない。

## 0. どこへ進むか決める

`git branch -a` で全ブランチを見て、**プロダクトのコードがあるか**を確認する。
**同梱の見本（`apps/web`）はプロダクトのコードに数えない。**
選択肢をユーザーに並べて選ばせない。ここで自分で決める。

- **ルールそのもの（AGENTS.md / skill / CI / 見本）を直す回**だとユーザーが言った
  → setup は何もせずに終わる。指示された作業をそのまま行う。
- **プロダクトのコードがある**（既定でないブランチにある場合も含む）
  → そのブランチに移り、**手順 A** へ。手順1〜5は実行しない。
- **無い** → **手順1** から順に実行する。

## 1. 何を作るか聞く

ユーザーに聞く。推測で埋めない。

- 完成したら誰が使うか（自分だけ / 特定の人に渡す / 不特定多数）
- その人はどうやって開くか（ブラウザで URL / 手元で起動）

## 2. 雛形を作る（中身は空）

構成の既定値。外部の縛り（指定のクラウド、既存システムとの接続、指定の言語）があるときだけユーザーに確認して変える。

- 画面が主: TypeScript / Next.js / pnpm / Vercel
- データ処理・AI が主: Python / FastAPI / uv（既定は手元起動。公開が必要ならデプロイ先をユーザーに聞く）
- 静的な1枚もの: HTML / CSS / JS（ビルドなし。開発サーバ欄は「なし」）

やること:

- **先に同梱の見本（`apps/web`）を消す。** 残すと、手順4で作るチェックが見本の方を
  見に行って必ず赤になる。見本を消したら `pnpm-workspace.yaml` `tsconfig.base.json` など見本専用の
  設定も一緒に消す（新しい雛形が同じ構成を使うなら、そちらのものとして作り直す）。
- 空のトップページ（または最小のエントリポイント）だけを作る。機能は書かない。
- ただし**手順4のテストが呼ぶための関数を1つだけ置く**（例: 受け取った文字列をそのまま整形して返す）。
  これは機能ではなく、渡し方とチェックが本当に動いているかを確かめるための取っ掛かり。
- 2箇所以上で使う文言・料金・URL の置き場所を1つ作る（例 `src/content.ts`）。
- `README.md` に起動手順を書く（必要なソフト / インストール / 起動コマンド）。
- ブラウザで開くものは、ホスティングとの接続が必要。**この接続はユーザーがブラウザで行う。** 手順を示して待ち、完了を確認してから次へ進む。

## 3. 渡し方を1回通す

中身が空のまま、1で決めた経路を通す。

- ブラウザで開くもの: push して、公開 URL が実際に開くことを確認する
- 手元で起動するもの: `README.md` の手順だけを見て、開発環境の外から起動できることを確認する

通らないうちは次に進まない。

## 4. チェックを作る

- lint を入れる（JS/TS なら eslint、Python なら ruff）。
- **1ファイルあたりの行数上限を明示的に有効にする**（eslint の `max-lines` は既定では無効。Python はファイル行数のルールが無いので CI に行数チェックを1ステップ足す）。上限は 300 行程度から始める。
- **わざと上限を超えるファイルを1つ作り、赤になることを確認してから消す。** 確認していない設定は入れていないのと同じ。
- テストを1件書いて通す。手順2で置いた関数を実際に呼び、戻り値を検証するものにする。中身のないテストは置かない。
- CI を作る。`on: [push, pull_request]`。すべてを集約する job を1つ置き、**job id を `ci-green`** にする（`name:` は設定しない。ここがずれると必須チェックが永久に待ち状態になる）。
- 見本向けに書かれていたワークフローを、この案件のものに直す。`codeql.yml` の言語、`.github/dependabot.yml` の対象。**対象が無いものは消す。** 公開URLができたら `presets/prod-smoke.yml` を `.github/workflows/` にコピーし、`PROD_URL` / `MARKER` を書き換える。
- 実行コマンドを AGENTS.md の「コマンド」節に書き写す。CI と同じコマンドにする。

## 5. 引継ぎ先を作る

- `docs/handoff.md`: ①今回実施したこと ②今回のトラブル ③次回やること
- `docs/failures.md`: 日付 / 事象 / 根因 / 教訓

**この手順4までが全部終わってから作る。**（既にある場合は、中身を今回のもので上書きする。
`docs/failures.md` は append-only なので既存行を消さない。）

## 6. 未記入を埋め切る

AGENTS.md に「未記入」が残っていないか確認する。該当が無い欄は「なし」と書く。ここを残すと毎セッション setup が発火する。

`docs/handoff.md` の③に「公開するなら setup の手順7」と書いておく。

## 7. 公開するときだけ（初期設定では実行しない）

無料プランでは、**Private のリポジトリに branch protection も Secret Protection も掛からない**。Public にして初めて効く。Public 化は取り消せないので、可否は必ずユーザーに確認する。

Public にしたら:

- Settings → Security → Code security で Secret Protection と Push protection を Enable
- Settings → Rules → Rulesets → New branch ruleset。次の4点はどれか1つでも外すと、作っても効かない。
  1. Enforcement status を Active にする（既定は Disabled）
  2. Target branches で Include default branch を選ぶ（未設定だと 0 targets のまま）
  3. Require status checks to pass に `ci-green` を追加する
  4. Require a pull request before merging も入れる（Required approvals は 0 のまま）。無いと main への直 push で CI を迂回できる

GitHub の画面が変わっていたら、上の項目名で検索して読み替える。この設定は GitHub Actions からは変更できないので、人が管理者権限で行う。

## A. 既にコードがあるとき（取り込み）

**雛形は作らない。既存の構成・依存・設計を変えない。** ユーザーに確認せず実行し、終わってから報告する。

1. AGENTS.md の「コマンド」節を、**実在のコードから読み取って**埋める（`package.json` の scripts /
   `Makefile` / `pyproject.toml` / `Cargo.toml` / 既にある CI 定義）。想像で書かない。該当が無い欄は「なし」。
   - テストは「1件だけ走らせる形」も必ず書く。毎回全件回さないため。
   - 環境変数は**名前だけ**書く。値は書かない。
   - 2箇所以上で使う文言・値の置き場所が無ければ、**1つ作って**そのパスを書く。
2. 見本（`apps/web`）を消す。**プロダクトのコードが手元のブランチに実在することを
   確認してから**行う。プロダクトが同じ構成を使っている場合、`pnpm-workspace.yaml` `pnpm-lock.yaml`
   `tsconfig.base.json` は**プロダクトの資産なので残す**。判断が付かないファイルは残す。
   削除は独立したコミットにして、後から戻せるようにする。
3. CI をこのプロジェクトのコマンドに書き換える（手順4のルールに従う。**`ci-green` は必ず残す**）。
   緑にするためにチェックを削らない・弱めない。`codeql.yml` の言語、
   `dependabot.yml` の対象も実態に合わせ、対象が無いものは消す。公開URLができたら
   `presets/prod-smoke.yml` を `.github/workflows/` にコピーする（手順4と同じ）。
4. 見本向けに出ている依存更新の PR が残っていれば閉じる。放置すると自動マージで既定ブランチに入る。
5. `docs/handoff.md` が無ければ作る。プロダクトが独自の引継ぎ記録（`memory.md` 等）を既に持って
   いるなら**そちらを正とし**、`docs/handoff.md` にはその参照先を1行書くだけにする（二重管理しない）。
   別プロジェクトの記録が残っていたら、要約せず破棄して初期化する。
6. 手順6（未記入の埋め切り）へ進む。
